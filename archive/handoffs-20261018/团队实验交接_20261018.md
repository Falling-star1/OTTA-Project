## 6. 已完成的 Source 小样本结果

Source 指**模型参数完全冻结、不进行测试时更新**的对照。

### 6.1 两次运行的统一配置

- 模型：Qwen2.5-7B-Instruct，FP16，物理 GPU 0、1。
- 数据：每套固定前 16 条，共 48 条。
- 输入上限：1024 token；greedy；seed=42；batch size=1。
- 模板：TLM qwen，保留数据集已有的任务提示文本。
- 两次运行仅将生成上限由 128 调整为 512 token。
- 两次均无输入截断、无空预测，均出现 `SOURCE_SMOKE=PASS`。

### 6.2 指标与长度限制

| 数据集 | 指标（0–1） | 128-token 结果 | 512-token 结果 | 达到生成上限：128 → 512 |
|---|---|---:|---:|---:|
| GeoSignal | ROUGE-Lsum | 0.2183997716 | 0.2035015229 | 11/16 → 3/16 |
| Dolly | ROUGE-Lsum | 0.2672988058 | 0.2689448351 | 7/16 → 3/16 |
| GSM8K | EM | 0.0625 | 0.7500 | 16/16 → 0/16 |

512-token 运行的两卡峰值显存为 6472.0 MiB、8256.5 MiB。这是 Source 推理记录，不能据此保证训练显存也足够。

128-token GSM8K 样例在中间推导处截断；512-token 样例可以生成结论，说明此前的长度限制明显影响结果。
GeoSignal 和 Dolly 的 512-token 版本仍各有 3 条达到上限。后续对照固定相同长度并继续记录此项，不按哪次分数高来选择长度。

**48 条都是流程调试样本，不是随机抽样统计报告，也不是完整论文复现成绩。**

### 6.4 指标口径和已知限制

GeoSignal / Dolly 使用 ROUGE-Lsum，按照上游脚本处理 `<n>` 和英文句子切分，并使用词干化。
GSM8K 使用原仓库 `extract_gsm8k_answer_number`，其规则会提取回答末尾数值，再与参考答案比较。

已发现一个具体案例：模型在中间算出剩余总量 23，但最后又讨论每天的数量，并以原配额 50 结尾，评分器提取为 50。该例涉及回答偏离和提取规则限制，不据此手工改为正确。
当前保留原评分器；若后续增加其他提取规则，应单独命名和报告，所有方法使用相同口径，不能只为某个方法改分。

## 7. 下一步：Tent 单步预检

### 7.1 本次验证什么

这一步只检查一次无标签更新是否正确，不计算正式任务得分：

1. 读取固定 GSM8K 第 0 条的 instruction/input，不把参考答案传给适应函数。
2. 使用 TLM qwen 模板，greedy 生成最多 80 token。
3. 固定生成前缀，重新前向计算生成位置的全词表预测熵。
4. 仅更新 q/v LoRA 参数，Adam 执行一步。
5. 检查梯度有限、两张卡均参与、部分 LoRA 确实更新、全部基础权重不变。
6. 恢复 adapter 初值、清空优化器状态，验证重置正确。

**80 token 是适应目标的前缀预算，512 token 是 Source/后续评测的生成预算，二者不能混用。**

### 7.2 固定参数

| 项目 | 本次值 |
|---|---|
| 方法标记 | `Tent-text-LoRA engineering adaptation` |
| 输入样本 | 固定版本 `gsm8k_5k` 的 `source_index=0` |
| 基础参数 | FP16，冻结 |
| LoRA 目标 | `q_proj`、`v_proj` |
| LoRA 参数 | rank=8，alpha=16，dropout=0；A 高斯初始化，B=0 |
| 可训练参数 | 预期 2,523,136 个，FP32；运行时核对名字与数量 |
| 优化器 | Adam，lr=1e-6，betas=(0.9,0.999)，eps=1e-8，weight_decay=0 |
| 更新次数 | 一步 |
| 熵计算 | FP32、自然对数、全词表；有效生成位置取平均 |
| 掩码 | 排除提示位置、PAD、停止符及其之后的位置，正确处理因果位移 |
| 显存设置 | 非重入梯度检查点；反向时关闭 KV cache |

TLM 附录给出了 80-token 熵适配描述，但作者 Tent 基线究竟更新哪些参数，尚未从基线代码确认。
本次 LoRA 参数化和未单独披露的超参数属于记录清楚的工程选择，不能宣称完全还原了作者的 Tent 基线。

| SAR / DeYO | 阅读各自原论文和官方实现，提出文本迁移方案 | 原方法与文本版本的对应表、关键假设、实现和测试 | 不能仅替换模型名称；改动可解释、可复查 |

当前对接人优先维护环境、版本和统一运行入口；方法负责人与评测负责人先对齐协议再各自实现。
不要让各方法分别使用不同模型版本、提示模板、数据文件或答案提取规则。

### 8.1 推荐推进顺序

1. **Tent 单步真实 GPU 验收**：确认适应更新正确且显存可行。
2. **Qwen 三数据集小样本对照**：每套 16 条，比较 Source 与 Tent。
3. **EATA / SAR / DeYO 的小样本验证**：复用统一输入/评测框架，单独记录各方法的模块和差异。
4. **冻结正式协议并扩展样本规模**：正式配置下重跑 Source 和各方法，不直接把前 16 条调试成绩当正式对照。
5. **补齐 Llama 模型的同口径实验**：访问申请与模型准备可与前几步并行。
6. **构造 proxy pool 并比较**：阅读与协议设计可提前进行，实际效果比较需建立在可靠基线上。

## 9. 统一实验协议与协作约定

### 9.1 适应与评测

- 当前正式比较拟采用 TLM 的 **offline** 思路：先用该数据集全部指定适应输入更新，再统一生成并评测。
- 不把“逐条先更新再立刻评分”的 online 流程与 offline 结果混在一个表中。
- 每个数据集开始前，从相同基础模型和新初始化 adapter/optimizer 开始，不能继承上一个数据集的更新状态。
- 测试输入可以按已声明的测试时适应协议使用；参考答案仅用于评测，不能进入适应损失、样本筛选或超参数选择。
- 保留数据文件哈希、原始索引、顺序和随机种子；前 16 条是调试集，不是已经确定的正式验证集。
- 正式输入长度、适应步数、学习率、参数集合等需要另行冻结；目前的 1024/512 设置是已有调试配置。
- 若正式配置变化，Source 与方法结果都应在新配置下运行后比较。

### 9.2 目录、依赖与版本

- 在独立项目环境中安装包，禁止在 base 下运行项目 `pip install`；统一使用 `python -m pip` 确认解释器归属。
- 现有包版本已固定。新增依赖由环境负责人统一准备离线包并记录锁定版本，不直接覆盖环境升级。
- 服务器此前外网访问出现证书主机名不匹配和超时，当前运行流程按离线方式组织。
- 模型、数据、缓存、checkpoint 和实验结果保留在 `/data/chuwenjing`；核心代码放在 home 下的项目目录。
- 不覆盖基础权重和已有结果目录；新运行使用独立时间戳目录，并在日志中打印输出位置。
- 不随意修改离线包内容；SHA256SUMS 和已安装运行副本的 cmp 检查用于识别不同版本。需要改动时新建可识别版本并更新校验清单。
- VS Code 曾提示系统版本不受支持，但已有成功连接记录。保留可用会话，连接兼容性由负责人统一处理。

### 9.3 GPU 与日志

- 启动前运行 `nvidia-smi`，并在组内协调卡号。空闲检查不等于 GPU 被正式预留。
- CUDA_VISIBLE_DEVICES 的物理卡号与进程内部 `cuda:0/1` 编号可能不同，运行记录两者都保留。
- 不重复启动同一个实验，不结束他人的进程，不在未核对所属运行时批量清理 GPU。
- 后台实验使用 nohup，日志写入 `/data`；断开 SSH 后可重新连接并查看同一日志。
- 失败记录也保留。没有明确 PASS 或完整产物时，状态写“运行中/失败/待验收”，不写“完成”。
